IMPLEMENTATION PROMPT - RUN 1
Tamil AI Voice-Ordering Agent Framework: Config Engine + Order Dashboard (Prototype Demo)
=========================================================================================

ROLE
You are a senior core-PHP engineer. Build the whole of Run 1 below in ONE run, without asking questions. Where something is unspecified, choose the simplest sensible option and list it under "Deviations / assumptions" in your final report.

GOAL
A reusable framework where adding a shop = adding ONE config file and ZERO engine changes. Run 1 has NO voice integration. It delivers the config engine, MySQL schema, a manual order-import page (simulating the future webhook), and an owner dashboard, all demo-ready with seed data.

The agreed config schema is pasted in full at the END of this prompt (section "SCHEMA REFERENCE"). Implement against it exactly. Do not rename its keys. The two example shops in it (panipuri_stall_01, grocery_store_02) must be saved as seed config files and loaded through the engine.

HARD STACK RULES
- Core PHP 8.x + MySQL via PDO only. NO frameworks, NO Composer packages required (a simple PSR-4-style autoloader written by hand is fine).
- OOP, DRY, SOLID. Every class has one responsibility. Depend on interfaces where the schema notes call for them (ShopConfigRepository, VoiceProviderInterface).
- PDO prepared statements for EVERY query. Exceptions mode on. No string-built SQL with user input.
- No secrets in code. DB host/user/password/name and any future API keys come from a config/.env.php (or .env) file that is NOT committed; ship config/env.example.php and a .gitignore entry for the real one. ElevenLabs API key is read from env, never hardcoded.
- UTF-8 / Tamil-safe end to end: DB and tables utf8mb4 / utf8mb4_unicode_ci, PDO charset=utf8mb4, `header('Content-Type: text/html; charset=utf-8')`, `<meta charset="utf-8">`, json_decode/encode with JSON_UNESCAPED_UNICODE, all output escaped with htmlspecialchars(..., ENT_QUOTES, 'UTF-8'). Use mb_* string functions where length/case matter. Tamil text must display correctly in seed data, forms and the dashboard.
- Runs on Wamp (Windows, Apache + PHP + MySQL, project in C:\wamp64\www\voiceshop\). No CLI-only tools, no Docker, no Node. Use forward slashes and __DIR__ for paths. Provide a .htaccess only if needed and make it optional (the app must also work without mod_rewrite, using plain URLs like index.php?page=orders).

PART 1 - CONFIG ENGINE
1. ShopConfigRepositoryInterface with FileShopConfigRepository (reads config/shops/{shop_id}.json). Strip all keys starting with "_comment" on load (recursively). Design so a MySQL-backed repository could be added later without changing callers (do not build it now).
2. ConfigValidator, run on every load, returns errors (block) and warnings (allow). Implement all checks from schema note 4:
   - required top-level keys present
   - every code in enabled_languages has a block in languages (partial allowed); default_language is in enabled_languages
   - default_language block is COMPLETE: voice, persona, greeting, closing, delivery_notice, agent_may_say_after_order, products, dashboard_customer_text (with order_received, order_confirmed, out_for_delivery)
   - every languages[code].products key matches a real sku in shop products
   - every product in the default language block has a display_name
   - voice.selected is "male" or "female" AND exists in voice.options (where a voice block exists)
   - a voice_id starting with REPLACE_ is "unfilled": emit a WARNING (not an error)
   - price_visibility in [owner_only, customer_ok, never_show]
   - status_flow uses only listed statuses; statuses equals the six agreed codes
   - required_fields address.must_have is a subset of address.parts
   Invalid config must show a clear error list on a "Config Health" page (see Part 4), never a PHP fatal.
3. LanguageResolver: resolve(shopConfig, langCode, key) reads languages[langCode][key]; on a miss reads languages[default_language][key]; on a second miss returns null and logs (to a log file under storage/logs, created if missing). If langCode is not in enabled_languages, use default_language. Support dotted keys (e.g. "dashboard_customer_text.order_confirmed", "products.rice_ponni.display_name"). Per-key fallback, so a partial block works (the en-IN block of grocery_store_02 must resolve closing/delivery_notice from ta-IN).
4. Voice resolution: VoiceResolver returns the final voice_id for (shop, language): reads languages[code].voice.options[selected].voice_id; if that is a REPLACE_ placeholder, fall back to the default_language block's selected voice (and flag it as a fallback in the result object). Switching gender must be a config edit only.
5. VoiceProviderInterface (e.g. synthesize(text, voiceId, languageCode): string and name(): string). ElevenLabsProvider implements it as a STUB: it must NOT make any network call in Run 1; synthesize() throws a clear NotImplementedYet / returns a stub result with a docblock saying the real call comes in a later run. VoiceProviderFactory::make(shop.voice_provider) maps "elevenlabs" -> ElevenLabsProvider; unknown key -> clear exception. Adding a provider = new class + one map entry (or registration), no engine change.
6. A "Config Health" page lists each shop: validation errors/warnings, enabled languages, per-language resolved voice (provider, gender, voice_id or "placeholder -> fell back to ta-IN"), and a small live demo of LanguageResolver fallback (e.g. show grocery_store_02 en-IN closing resolved from ta-IN with a "fallback" badge).

SHOP CONFIG SCHEMA (voice-ordering framework) - MULTI-LANGUAGE EDITION
======================================================================
One file (or one DB row with a JSON column) per shop. Engine code never changes.
Adding a shop = add one config. Adding a language = add ONE block to the shop's
"languages" map. JSON does not allow comments, so comments below use "_comment"
keys / the notes section. Strip "_comment" keys when loading.

LANGUAGE MODEL
  - shop.default_language  : fallback language (ta-IN for both examples below).
  - shop.enabled_languages : codes the shop actually takes calls in.
  - shop.languages         : map keyed by language code (ta-IN, en-IN, hi-IN...).
    Every customer-facing string lives inside a language block: greeting,
    closing, persona, voice choice, delivery notices, agent-spoken lines,
    product display names + spoken aliases, and dashboard customer-facing text.
  - FALLBACK RULE: if a key is missing in the active language block, the engine
    reads it from default_language. A partially filled block is valid config.
  - Language-independent product fields (sku, unit, allowed_units, price,
    price_visibility, options) stay at shop level. Nothing about money, units
    or rules ever lives inside a language block.

VOICE GENDER MODEL
  - Each language block has a "voice" object:
      "voice": {
        "selected": "female",
        "options": {
          "female": { "voice_id": "..." },
          "male":   { "voice_id": "..." }
        }
      }
  - The owner flips "selected" between male and female; the engine reads
    voice.options[voice.selected].voice_id. No engine change to switch gender.
  - An option whose voice_id is still the REPLACE_ placeholder counts as
    unfilled: the resolver falls back to the default_language block's selected
    voice, and the validator warns.

LAYER USE
  Voice layer      : languages[code].persona / greeting / voice, products (for the prompt)
  Extraction layer : products, languages[code].products aliases, required_fields, units
  Dashboard layer  : statuses, delivery, payment, whatsapp, rules, languages[code].dashboard_customer_text
  Webhook layer    : shop_id (routes the post-call payload to this config)

NOTES FOR CORE PHP + MYSQL
--------------------------
1. Storage: table shops(shop_id PK, config JSON, updated_at). Or one file per
   shop in /config/shops/{shop_id}.json. Load through a ShopConfigRepository
   interface (file or MySQL implementation, same interface).
2. Language resolution: one LanguageResolver class. resolve(shop, langCode, key)
   reads languages[langCode][key]; on a miss it reads
   languages[default_language][key]; on a second miss it returns null and logs.
   Call language is picked from the caller's choice (IVR / first utterance) and
   must be in enabled_languages, else default_language. Adding a language never
   touches the resolver - it is a data lookup.
3. Voice resolution: the resolver reads languages[code].voice. If the selected
   gender's voice_id is a REPLACE_ placeholder (unfilled), it falls back to the
   default_language block's selected voice. Switching gender = the owner edits
   one "selected" value; switching provider = edit voice_provider; both are
   config, not code.
4. Validate on load with one ConfigValidator: required keys, every code in
   enabled_languages has a block (even partial), default_language block is
   COMPLETE (fallback target must be full), voice.selected is male or female
   and exists in voice.options, price_visibility in
   [owner_only, customer_ok, never_show], status_flow only uses listed statuses,
   every languages[code].products key matches a real sku in shop products.
5. Voice: VoiceProviderInterface; ElevenLabsProvider is one class. Factory reads
   voice_provider. The provider class receives the resolved voice_id (language
   + gender already picked by the resolver). New provider = new class, no engine
   change (Open/Closed).
6. Prompt builder reads languages[code].persona / greeting / closing / products
   (display names + aliases) plus shop-level products (units, price rules) and
   rules. Rule "agent_never_confirms" is injected into the system prompt AND
   checked again by the extraction layer (flag any transcript line where the
   agent promised stock/price/delivery).
7. Extraction output (same shape for every shop and every language):
   { "shop_id", "call_id", "language": "ta-IN",
     "customer": {name, phone, address{}},
     "items": [{sku, qty, unit, options{}, raw_text}],
     "delivery_choice", "payment_choice", "requested_time",
     "missing_fields": [], "flags": [] }
   missing_fields not empty -> status NEEDS_DETAILS, else AWAITING_MERCHANT_APPROVAL.
   Extraction matches against the ACTIVE language's aliases plus skus, and
   stores language so the dashboard can pick the right customer-facing text.
8. price_visibility only affects what the agent may say, in any language.
   Dashboard always shows the price to the owner.
9. Idempotency: webhook stores call_id with a UNIQUE key so a retried webhook
   never creates a duplicate order.
10. Suggested tables: shops, orders(shop_id, call_id UNIQUE, language, status,
    order_json, created_at), order_items, order_status_log(order_id, from, to,
    by, at).
